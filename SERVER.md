# chat_multi_cli — мессенджер для мастеров (заявки из Telegram)

## 1. Суть проекта

Есть Telegram-бот, принимающий заявки от клиентов. Клиент пишет боту, бот создаёт заявку
и передаёт её мастерам. Мастера **не имеют Telegram-аккаунтов** и не будут их заводить.

Нужно ПК-приложение (клиент для мастера), которое:

- опрашивает сервер на новые заявки и новые сообщения по заявкам;
- отправляет ответы клиенту (клиент видит их как сообщения от бота: «Ответ от Фёдор Семёнов, 12:33: ...»);
- хранит локальный кэш истории (SQLite), чтобы открытая заявка открывалась мгновенно;
- умеет подключать второго мастера в ту же заявку (равные права, оба пишут в один чат с клиентом);
- умеет закрывать заявку.

Сервер — **отдельный проект**: Telegram-бот + API. Репозиторий `chat_multi_cli` содержит
только клиента и эту спецификацию.

### 1.1. Цеха

Мастера распределены по цехам (слесарный, кузовной, ...). Клиент в Telegram при создании
заявки выбирает: **всем мастерам** или **мастерам конкретного цеха**.

- Заявка «всем» (`workshop_id = null`) видна в общей ленте всем мастерам.
- Заявка на цех видна только мастерам этого цеха.
- Кто принял заявку первым — тот `owner`. Второй мастер подключается явно по id.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Мастер | пользователь клиента, `master_id` |
| Цех | `workshop_id`, принадлежность мастера |
| Экземпляр клиента | `instance_id` (UUID, генерируется при первом запуске), фактически идентификатор рабочего места |
| Заявка | `ticket` — диалог клиента с одним или несколькими мастерами |
| Участник заявки | мастер с доступом к заявке, роль `owner` / `collaborator` |
| Сообщение | `message` — реплика клиента, мастера или системная |
| Лента | список заявок, доступных мастеру прямо сейчас (`ticket.status = new`) |
| Seq | сквозной монотонный номер события в ленте мастера, «курсор» синхронизации |

## 3. Архитектура

```
   Клиент (Telegram)                Сервер (бот + API)              Клиент мастера (chat_multi_cli)
        │                                  │                                   │
        │── сообщение / заявка ───────────>│                                   │
        │                                  │─── poll GET /sync (long-poll) ───>│
        │                                  │                                   │
        │<── «Ответ от Фёдор Семёнов…» ────│<── POST /messages ─────────────────│
```

Клиент — **только получатель и отправитель**, вся бизнес-логика и форматирование текста
для Telegram живут на сервере. Клиент никогда не общается с Telegram API напрямую.

### 3.1. Слои клиента

```
┌──────────────────────────────────────────────┐
│ UI (список заявок / диалог / ввод)            │  ← только читает из БД
├──────────────────────────────────────────────┤
│ Store: SQLite (WAL) — единственный источник  │  ← проекция состояния
│   правды для UI, транзакции на пачку событий │
├──────────────────────────────────────────────┤
│ Sync loop: long-poll /sync → запись в БД    │  ← фоновая задача, не блокирует UI
├──────────────────────────────────────────────┤
│ API client (HTTP, retry + backoff, cursor)   │
└──────────────────────────────────────────────┘
```

## 4. Ключевое решение: лента событий вместо «есть ли новое?»

Исходная постановка предполагала `hasNewTickets` / `hasNewMessages`. Так делать не надо:

- между проверкой и чтением событие может пропасть (гонка), либо появиться дважды;
- невозможно догрузить историю «с прошлого раза» после обрыва связи;
- будильники и звуки в UI придётся делать на глазок.

Поэтому ядро протокола — **один long-poll по событиям с курсором** (`GET /v1/sync`).
Клиент присылает `cursor`, сервер отдаёт все события после него. Ничего не теряется,
дубликаты отсеиваются по `seq`.

## 5. Модель данных

```
Master        (id, full_name, workshop_id, instance_id, is_active)
Workshop      (id, name)
Client        (id, tg_chat_id, display_name, phone?)
Ticket        (id, client_id, workshop_id|null, status, owner_master_id,
               subject, created_at, updated_at, closed_at, close_reason)
TicketMember  (ticket_id, master_id, role: owner|collaborator, joined_at)
Message       (id, ticket_id, seq, sender: client|master|system,
               sender_master_id, sender_name, text, created_at,
               delivery, read_at)
Attachment    (id, ticket_id, message_id, kind, filename, mime_type,
               size, width, height, source: master|client, storage_key)
Event         (seq, master_id, type, ticket_id, data, ts)   ← лента
```

### 5.1. Статусы заявки

| Статус | Значение |
|---|---|
| `new` | никем не принята, видна в ленте |
| `in_progress` | есть owner, идут переписка и работа |
| `closed` | закрыта мастером |

Переходы: `new → in_progress` (accept), `in_progress → new` (release — вернуть в общую ленту),
`in_progress → closed` (close), `closed → in_progress` (reopen).

## 6. API сервера

Базовый URL: `https://<host>/v1`. Формат: JSON, UTF-8, `Content-Type: application/json`.

Заголовки всех запросов, кроме первого обращения к `/session`:

```
X-Instance-Id: 3f2a...-uuid
X-Client-Version: 0.1.0
```

### 6.1. Идентификация и мастера

Безопасность в v1 не предполагается: `instance_id` — это белый список на сервере.
Механизм замкнут на будущее: сервер может выдавать токен, клиент будет его хранить,
это не меняет структуру запросов.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/session` | Привязать экземпляр клиента к мастеру (регистрация/вход) |
| `GET` | `/session` | Текущий профиль + актуальный курсор |
| `PATCH` | `/session/profile` | Изменить ФИО или цех |
| `GET` | `/workshops` | Список цехов (для выбора при первом запуске) |
| `GET` | `/masters` | Справочник мастеров (для подключения второго) |
| `GET` | `/masters/{id}` | Карточка мастера |

#### `POST /v1/session`

Тело:

```json
{
  "instance_id": "3f2a9c10-...-uuid",
  "full_name": "Фёдор Семёнов",
  "workshop_id": "body",
  "client_version": "0.1.0",
  "platform": "win32"
}
```

Ответ `200`:

```json
{
  "master_id": "m_17",
  "profile": { "id": "m_17", "full_name": "Фёдор Семёнов", "workshop_id": "body",
               "workshop_name": "Кузовной", "is_active": true },
  "token": null,
  "cursor": 4820,
  "server_time": "2026-10-01T12:00:00Z",
  "telegram": { "bot_username": "sto_bot" }
}
```

Ошибки: `403 instance_not_whitelisted` (id неизвестен серверу — нужно добавить в белый список),
`422 validation_error` (пустое ФИО, невалидный `workshop_id`).

#### `GET /v1/masters`

Параметры: `query` (поиск по ФИО), `workshop_id`, `include_self`, `limit` (по умолчанию 50).

```json
{
  "masters": [
    { "id": "m_17", "full_name": "Фёдор Семёнов", "workshop_id": "body",
      "workshop_name": "Кузовной", "online": true, "active_tickets": 2 }
  ]
}
```

`online` — обновляется сервером по heartbeat; нужен, чтобы не подключать офлайн-мастера.
`instance_id` наружу не отдаётся.

### 6.2. Синхронизация (ядро)

#### `GET /v1/sync`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `cursor` | int | `0` | последний обработанный `seq` |
| `limit` | int | 200 | макс. событий за раз |
| `wait` | int | 25 | long-poll, сек (0 — не ждать) |
| `ticket_id` | string | — | фильтр: только события одной заявки |

Ответ `200`:

```json
{
  "events": [
    { "seq": 4821, "type": "ticket.created", "ts": "2026-10-01T12:00:01Z",
      "ticket_id": "t_9f2c", "data": { "...": "..." } },
    { "seq": 4822, "type": "message.created", "ts": "2026-10-01T12:00:04Z",
      "ticket_id": "t_9f2c", "data": { "...": "..." } }
  ],
  "cursor": 4822,
  "has_more": false
}
```

Семантика:

- если события есть — отдаются сразу; если пусто — сервер держит соединение до `wait` секунд;
- по истечении `wait` без событий допустим `204 No Content` (клиент сразу переспрашивает);
- `wait=0` — ответ без удержания: `200` с пустым списком (обычный опрос);
- висящий клиент держит один поток пула и одно соединение, поэтому за обратным
  прокси `proxy_read_timeout` должен быть больше `wait`, иначе клиент получит
  504 вместо события;
- доставка **at-least-once**: клиент обязан дедуплицировать по `seq`;
- порядок строго по возрастанию `seq`;
- `seq` сквозной по серверу, но клиент получает только свои события.

Ошибка `410 Gone`:

```json
{ "error": { "code": "cursor_expired",
             "message": "События старше курсора уже недоступны",
             "details": { "min_available_cursor": 4900 } } }
```

Клиент при этом делает полный ресинк: `GET /tickets` + догрузка последних N сообщений
по открытым заявкам, и выставляет курсор в ответ.

#### Типы событий

| `type` | Когда | `data` |
|---|---|---|
| `ticket.created` | новая заявка попала в ленту мастера | `ticket` (brief) + первые сообщения клиента |
| `ticket.accepted` | мастер принял заявку | `owner_master_id`, `owner_name` |
| `ticket.released` | заявка возвращена в общую ленту | `by_master_id`, `reason?` |
| `ticket.closed` | закрыта | `reason?`, `by_master_id` |
| `ticket.reopened` | переоткрыта | `by_master_id` |
| `ticket.updated` | изменены поля (тема, цех) | `patch` |
| `ticket.member_added` | подключён второй мастер | `member` |
| `ticket.member_removed` | мастер отключён | `master_id` |
| `message.created` | новое сообщение (от клиента, мастера или системное) | `message` |
| `message.updated` | сменился статус доставки / клиент прочитал | `message_id`, `delivery`, `read_at` |
| `masters.directory_changed` | изменилось ФИО/цех мастера | `master_id` (клиент обновляет кэш справочника) |

### 6.3. Заявки

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/tickets` | Список заявок: лента / мои / все |
| `GET` | `/tickets/{id}` | Карточка заявки с участниками |
| `POST` | `/tickets/{id}/accept` | Принять заявку (атомарно) |
| `POST` | `/tickets/{id}/release` | Вернуть заявку в общую ленту |
| `POST` | `/tickets/{id}/close` | Закрыть заявку |
| `POST` | `/tickets/{id}/reopen` | Переоткрыть заявку |
| `POST` | `/tickets/{id}/decline` | Скрыть заявку из своей ленты |
| `POST` | `/tickets/{id}/read` | Отметить прочитанным до `seq` |
| `POST` | `/tickets/{id}/members` | Подключить второго мастера по `master_id` |
| `DELETE` | `/tickets/{id}/members/{master_id}` | Отключить мастера от заявки |

#### `GET /v1/tickets`

Параметры: `scope` = `feed` (заявки в ленте, `status=new`, доступные мне) |
`mine` (где я участник) | `all`; дополнительно `status`, `workshop_id`, `query`
(поиск по теме/тексту), `limit` (50), `before` (курсор пагинации).

```json
{
  "tickets": [
    { "id": "t_9f2c", "status": "new", "workshop_id": null, "workshop_name": "Все цеха",
      "subject": "Левый баккер", "created_at": "2026-10-01T12:00:01Z",
      "updated_at": "2026-10-01T12:04:20Z",
      "client": { "id": "c_3", "display_name": "Иван П.", "phone": null },
      "owner": null,
      "members": [],
      "last_message": { "seq": 4822, "sender": "client", "preview": "Не могу пригнать..." },
      "unread_count": 3 }
  ],
  "next_before": null
}
```

#### `POST /v1/tickets/{id}/accept`

Тело пустое. Ответ `200` — карточка заявки со `owner` и составом участников.

Ошибки: `409 already_accepted` (с `details.owner_master_id`, `details.owner_name` —
клиент покажет «Заявку уже взял Фёдор Семёнов» и уберёт её из ленты), `404 ticket_not_found`,
`409 ticket_not_in_feed` (заявка уже не доступна), `403 ticket_closed`.

Атомарность обязательна: «кто первый принял — тот и делает». На уровне БД — условный
`UPDATE tickets SET status='in_progress', owner=? WHERE id=? AND status='new'` +
`INSERT ticket_members` в одной транзакции.

#### `POST /v1/tickets/{id}/members`

```json
{ "master_id": "m_42" }
```

Ответ `200`: `{ "member": { "master_id": "m_42", "full_name": "Пётр Кузнецов",
"role": "collaborator", "joined_at": "2026-10-01T12:10:00Z" } }`

Ошибки: `404 master_not_found`, `409 already_member`, `403 not_ticket_member`
(подключать может только участник заявки), `403 ticket_closed`, `409 workshop_mismatch`
(цех подключаемого мастера не совпадает с цехом заявки — если правило включим).

Новый участник сразу получает **всю историю**: сервер шлёт ему `ticket.member_added`,
клиент догружает историю через `GET /tickets/{id}/messages`.

#### `POST /v1/tickets/{id}/close`

Тело: `{ "reason": "Ремонт выполнен, авто готово" }` (необязательно; сервер формирует
для клиента текст «Заявка №t_9f2c закрыта мастером Фёдор Семёнов»).

Ошибки: `403 not_ticket_member`, `403 ticket_closed`, `404 ticket_not_found`.

#### `POST /v1/tickets/{id}/decline`

Тело: `{ "reason": "не наш профиль" }`. Скрывает заявку **только из ленты этого мастера**,
на остальных не влияет. Идемпотентно.

### 6.4. Сообщения

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/tickets/{id}/messages` | История сообщений (пагинация) |
| `POST` | `/messages` | Отправить сообщение клиенту |
| `POST` | `/tickets/{id}/read` | Отметить прочитанным |

#### `GET /v1/tickets/{id}/messages`

Параметры: `after_seq` (новые после), `before_seq` (история выше), `limit` (по умолчанию 100).

```json
{
  "messages": [
    { "id": "msg_555", "seq": 4822, "ticket_id": "t_9f2c",
      "sender": "client", "sender_master_id": null, "sender_name": "Иван П.",
      "text": "Не могу пригнать машину до пятницы",
      "attachments": [], "created_at": "2026-10-01T12:00:04Z",
      "delivery": "delivered", "read_at": "2026-10-01T12:07:10Z" }
  ],
  "has_more_before": true,
  "has_more_after": false
}
```

#### `POST /v1/messages`

```json
{
  "ticket_id": "t_9f2c",
  "client_msg_id": "b91d...-uuid",
  "text": "Ваша заявка принята, ожидайте до 14:00",
  "attachments": [ { "attachment_id": "a_71" } ]
}
```

- `client_msg_id` — UUID, генерируемый клиентом: ключ идемпотентности. Повтор с тем же id
  вернёт то же сообщение (а не дубль в Telegram).
- Ответ `202 Accepted`: `{ "message": { ... "delivery": "queued" } }`.
- Сервер ставит сообщение в FIFO-очередь Telegram (лимит ~1 сообщение в секунду на чат),
  форматирует его по шаблону «Ответ от {ФИО}, {время}: {текст}» и отправляет клиенту.
- Дальше приходят события `message.updated` со сменой `delivery`:
  `queued → sending → sent → failed`, и `read_at`, когда клиент прочитал.
- Ошибки: `403 not_ticket_member`, `403 ticket_closed`, `404 ticket_not_found`,
  `422 validation_error` (пустой текст и без вложений).

Офлайн-очереди отправки нет: если сети нет — отправка невозможна, приложение сообщает об этом.

### 6.5. Вложения

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/attachments` | Загрузить файл от мастера (multipart) |
| `GET` | `/attachments/{id}` | Скачать вложение (фото клиента тоже отсюда) |
| `GET` | `/attachments/{id}/meta` | Метаданные без скачивания |

`POST /v1/attachments` — `multipart/form-data`, поля: `file`, `ticket_id` (опционально).

```json
{ "attachment_id": "a_71", "kind": "photo", "filename": "photo.jpg",
  "mime_type": "image/jpeg", "size": 348122, "width": 1280, "height": 960,
  "source": "master", "created_at": "2026-10-01T12:11:00Z" }
```

Ограничения: до 20 МБ на файл, белый список mime-типов (jpg/png/webp/pdf/txt/doc/xls/zip).

Вложения от клиента: бот по `file_id` скачивает файл из Telegram и кладёт в то же хранилище;
мастер забирает его через `GET /v1/attachments/{id}` (доступ проверяется по участию в заявке).

## 7. Формат ошибок

Единый конверт на всех не-2xx ответах, кроме 401/403 транспортных:

```json
{ "error": { "code": "not_ticket_member",
             "message": "Вы не участник этой заявки",
             "details": { "ticket_id": "t_9f2c" } } }
```

| Код | HTTP | Когда |
|---|---|---|
| `validation_error` | 422 | невалидные поля |
| `unauthorized` | 401 | нет/невалидный `X-Instance-Id` |
| `instance_not_whitelisted` | 403 | экземпляр не в белом списке |
| `forbidden` | 403 | действие не разрешено роли |
| `ticket_not_found` | 404 | заявка не существует / не видна мастеру |
| `master_not_found` | 404 | мастер не найден в справочнике |
| `not_ticket_member` | 403 | мастер не подключён к заявке |
| `ticket_closed` | 403 | заявка закрыта |
| `already_accepted` | 409 | заявку уже взял другой мастер |
| `already_member` | 409 | мастер уже подключён |
| `ticket_not_in_feed` | 409 | заявка больше не в ленте |
| `cursor_expired` | 410 | нужен полный ресинк |
| `rate_limited` | 429 | слишком частые запросы, есть `Retry-After` |
| `server_error` | 500 | внутренняя ошибка, клиент ретраит с backoff |

## 8. Соглашения

- Время — ISO-8601 в UTC (`2026-10-01T12:33:04Z`), клиент показывает в локальной зоне.
- Все id — строковые с префиксом: `m_`, `t_`, `msg_`, `a_`, `w_` (неизменяемые, безопасны для URL).
- `seq` — целое, растёт монотонно, разрывов не бывает.
- Курсор хранится в SQLite клиента вместе с кэшем; при переустановке клиента — полный ресинк.
- Удаление сообщений и редактирование — вне v1 (спросить у заказчика).
- Идемпотентность: `POST /messages` по `client_msg_id`, `POST /read` и `POST /decline` — всегда.

## 9. Требования к клиенту (функционально)

1. Первый запуск: сгенерировать `instance_id`, запросить ФИО и цех, показать `instance_id`
   для добавления в белый список, вызвать `POST /session`.
2. Фоновый long-poll в отдельной задаче; события пишутся в SQLite одной транзакцией;
   UI читает только из БД и перерисовывается по сигналу.
3. Экран заявок: лента (`new`), мои (`in_progress`), закрытые; поиск; счётчики непрочитанных.
4. Экран диалога: история (догрузка вверх), индикатор доставки, статусы сообщений клиента
   («доставлено», «прочитано»), подписи авторов (мастер пишет «Фёдор», второй — «Пётр»).
5. Ввод текста, отправка по Enter, вложение файлов (drag&drop/кнопка), индикатор ожидания отправки.
6. Действия по заявке: принять, вернуть в ленту, закрыть, скрыть, подключить мастера
   (поиск по справочнику `GET /masters`), отключить мастера.
7. Реконнект: экспоненциальный backoff, автоперезапуск long-poll, индикатор «нет связи».
8. `cursor_expired` → полный ресинк без падения UI.
9. Конфиг в `~/.chat_multi_cli/config.json` (instance_id, ФИО, цех, токен, интервалы).
10. Логи: `~/.chat_multi_cli/logs/app.log` с ротацией; режим `--debug` пишет все запросы/ответы.

## 10. Стек клиента

**Решение:** PySide6 (Qt) + httpx + sqlite3 + QThread.

Обоснование выбора Qt: в мессенджере нужны нормальный показ фотографий из переписки
(превью, зум, открытие в полный размер), drag&drop файлов и таблица заявок с фильтрами.
В Tkinter всё это пришлось бы собирать вручную на `Pillow` и `tkinterdnd2`.
Серверная часть при этом остаётся на asyncio — клиент к ней отношения не имеет.

| Слой | Библиотека | Зачем |
|---|---|---|
| GUI | `PySide6` 6.11 | окна, таблица заявок, диалог, drag&drop, превью фото |
| HTTP | `httpx` 0.28 | keep-alive (критично для long-poll), таймауты, sync-клиент в QThread |
| БД | `sqlite3` (stdlib) | WAL, единственный писатель — Writer-поток |
| Потоки | `QThread` + сигналы | main thread только рисует, сеть в QThread |
| Валидация | `dataclass` (stdlib) | `pydantic` избыточен для 6.7 моделей |
| Логи | `logging` + RotatingFileHandler | пути берём из `%APPDATA%` вручную |
| Линт/тесты | `ruff`, `mypy --strict`, `pytest`, `respx` | мок HTTP без сети |

Из стандартной библиотеки дополнительно: `sqlite3`, `uuid` (генерация `instance_id`),
`logging`, `dataclasses`, `zoneinfo` (перевод времени в локальную зону).

### 10.1. Потоки и очередь

```
QApplication (main thread)
  ├─ MainWindow / TicketListView / ChatView / Composer
  └─ QTimer(50 мс) ──► Database.read_queries()
                              ▲
QThread: SyncWorker            │ только чтение
  ├─ GET /sync (long-poll)     │
  ├─► WriterQueue ─────────► WriterThread ──► Database.write_events()  (одна транзакция)
  └─ emit data_changed(seq) ──┘
QThread: SenderWorker
  └─ POST /messages ──► emit delivery_changed
```

Правило: **UI никогда не пишет в БД и никогда не ходит в сеть** напрямую.
SQLite-соединение нельзя использовать из нескольких потоков, поэтому запись идёт
через единственный Writer-поток с очередью. Это же даёт бесплатную транзакционность
пачки событий: пишем их все или не пишем ни одного, курсор двигается только после commit.

## 11. Реализация сервера (рекомендация)

- Python 3.11+, `aiogram 3` (бот) + `FastAPI`/`aiohttp` (API), `SQLAlchemy` + PostgreSQL
  (или SQLite, если нагрузка небольшая), `Redis` для очередей и `online`-статусов.
- Отдельный процесс-воркер: читает очередь отправки, шлёт в Telegram, обновляет `delivery`.
- Очередь на каждый клиентский чат: не чаще ~20 сообтекунд в секунду, с учётом лимитов Bot API.
- `instance_id` в белом списке — таблица `allowed_instances` (редактируется вручную SQL/adm-панелью).

## 12. Открытые вопросы

Требуют решения заказчика; часть влияет на API.

1. **Клиент пишет повторно при открытой заявке** — дописывать в неё или создавать новую?
   От этого зависит, нужен ли выбор «новая тема» в боте.
2. **Админка/роль админа?** Нужен ли режим, где администратор видит все заявки и может
   форсировать назначение мастера.
3. **«Прочитано клиентом»** — показывать ли мастеру галочку прочтения? (в API уже заложено `read_at`)
4. **Перегрузка мастера** — нужен ли лимит активных заявок на мастера или предупреждение
   «у вас 12 открытых заявок».
5. **Подтверждение цеха в Telegram** — клиент выбирает цех кнопками или пишет текстом?
   Нужна ли валидация на сервере.
6. **Показывать ли клиенту, что подключился второй мастер?** Фраза «К вашей заявке подключился
   мастер Пётр Кузнецов» — нужна ли.
7. **Эскалация** — нужен ли перевод заявки в другой цех (сейчас `workshop_mismatch` просто запрещает).
8. **Быстрые ответы/шаблоны** — нужны ли в клиенте заготовки фраз («мастер выехал», «нужен VIN»).
9. **Аудит** — нужен ли журнал действий мастеров (кто принял, кто закрыл, когда).
10. **Лимиты Telegram** — если мастер отправит 50 сообщений подряд, сервер должен схлопнуть их
    в одно или ограничить. Нужно ли это и как формулировать клиенту.
11. **Архив и удаление** — как долго хранить закрытые заявки, нужен ли экспорт истории.
12. **Уведомления Windows** — всплывающие тосты при новой заявке (требует отдельной обёртки/CLI-флага).

## 13. Порядок реализации

1. Скелет клиента: конфиг, `instance_id`, API-клиент, SQLite-схема.
2. Long-poll синхронизация + экран заявок (read-only).
3. Диалог: история, ввод, отправка текста, статусы доставки.
4. Приём/закрытие/возврат заявки.
5. Подключение второго мастера.
6. Вложения.
7. Уведомления, автообновление справочника, тюнинг UX.

Порядок для сервера: сущности и события → `/sync` → CRUD заявок → сообщения →
вложения → бот-обвязка (создание заявок, форматирование ответов, `read_at`).
